## 1. 六项字段与后端规则

| 页面字段 | 建议请求字段 | 类型 | 后端校验与用途 |
|---|---|---|---|
| 技能名称 | `skill_name` | string | 必填，去除首尾空白，1–128 字符；校验重复；保存为平台展示名和包内 `metadata.display_name` |
| 执行指令 | `instructions` | string | 必填，非空，最多 100000 字符；原文写入 `SKILL.md` 正文，具体步骤、业务约束、输入输出要求均由此提供 |
| 挂载知识库 | `knowledge_base_ids` | string[] | 选填，默认空数组；多选、去重；只接受真实知识库 ID，并逐项验证当前用户权限 |
| 资源上传入口 | multipart 的 `files` | file[] | 选填，统一入口、多文件；接收脚本、依赖包、文档、图片等，保留原始字节 |
| 资源使用说明 | `resource_usage` | string | 一个统一字段，最多 10000 字符；选择任意知识库或上传任意文件后，生成/调试前必填；说明何时使用、用途以及必要的调用方法 |
| 运行环境要求 | `compatibility` | string | 选填，最多 500 字符；填写时写入 YAML，未填写则省略；只记录要求，不安装依赖或配置运行环境 |

`skill_name` 是新表单的业务名称，允许中文，不能直接作为标准 Skill 的 YAML `name`。最终前端字段名可以通过适配层映射，不要求为了内部结构增加 UI 字段。

“资源使用说明”按最新截图设计为一个统一文本框，不再要求每个文件填写一份说明。有多个资源时，开发者可在同一文本中按名称分别说明；后端保留原文，不猜测各个文件的业务用途。

## 2. 不再由弹窗填写的信息

| 内部信息 | 来源与生成规则 |
|---|---|
| 标准技术名 `name` | 新技能由后端基于技能 ID 生成稳定的小写标识，如 `skill-<ID摘要>`；编辑已有技能沿用原技术名；改展示名不改包根目录标识 |
| 标准描述 `description` | 后端按确定性规则从技能名称和执行指令生成，不调用大模型、不补写业务规则；不超过 1024 字符 |
| `version` | 新技能默认 `0.1.0`；已有技能沿用原版本，本次不新增自动版本升级功能；不同构建通过 `build_id` 区分 |
| 创建者 | 已有 JWT 认证上下文；不接收前端提交的作者、维护人或用户 ID；本轮不增加登录页面 |
| 系统、团队、所属技能类、模型 Tier | 有实际平台上下文时继承；没有来源时省略对应元信息，不默认编造归属 |
| 文件用途和保存路径 | 后端上传适配层决定；不让用户填写服务器路径或内部 `role`、`upload_index` |
| `license`、`allowed-tools` | 本期继续省略 |

已实现的描述生成规则：`用于处理与「技能名称」相关的用户请求。` 加执行指令首个非空行的内容；合并空白并在 1024 字符内截断，执行指令正文仍完整保存。这里的“摘要”是确定性取首行/截断，不是大模型概括。该规则只提供可追溯的基础描述，质量取决于开发者填写的指令。

标准仍要求非空 `name`、`description`，并允许可选 `compatibility` 和字符串映射 `metadata`，因此删除 UI 输入框不等于删除标准字段。依据：[Agent Skills 规范](https://agentskills.io/specification)。

## 3. 名称唯一性

明确要求：名称必填，不能与已有技能重名，编辑时排除当前技能本身。

设计假设：暂按“平台内未删除技能”校验，不以当前浏览器列表、当前用户或当前团队作为唯一依据。这个范围是本方案的技术建议，尚不能当作产品已经确认的范围；前端交接时一并核对。

处理规则：

1. 展示名去除首尾空白；生成用于比较的规范化名称键，统一 Unicode 表示和英文大小写，不修改用户的展示文字。
2. 名称输入结束时可以调用检查接口；保存或生成时服务端再次检查。
3. 编辑时排除已通过权限校验的当前 `skill_id`；不能借用他人的 ID 绕过检查。
4. 重名返回 `skill_name` 字段错误，不返回冲突技能的私有详情。
5. 最终用数据库唯一约束防止并发重复，仅“先查询再创建”不能保证唯一。实施前检查旧数据是否有重名，并编写迁移；不自动改名、删除旧数据。
6. 如采用独立规范化名称键，软删除后释放其占用；恢复旧技能也要重新检查。

已实现：比较名称使用 `NFKC → 去首尾空白 → lower`，SHA-256 摘要存入唯一的 `name_key`；未删除但未启用的技能也占用名称。创建、编辑和新表单构建均检查，数据库唯一约束兜底；删除将键置空，恢复重新受唯一约束限制。构建在事务中先占用新名称，资源校验/生成失败回滚名称修改。前端有认证会话时可做服务端预检查，无会话时继续本地 mock，不注入 Token。

旧数据库必须先审计与回填，不能只添加空列。迁移工具默认只读审计，重名/无效名称时停止；不修改业务名称或删除记录。SQLite 旧表迁移及重跑已测试，本地联调库已迁移并建立经过完整性检查的迁移后快照；首次主文件拷贝不完整，不能称为迁移前恢复备份。MySQL 分支已提供，尚未连接团队 MySQL 验收。具体维护窗口、备份及 Aerich 协调见 [本批执行记录](skill-form-validation-progress.md)。批量 SQL/ORM update 不应绕过模型的名称键更新逻辑。

## 4. 知识库搜索、多选与生成

复用仓库已有 `GET /knowledge-bases/?search=<关键词>`：现有搜索覆盖名称和描述，返回当前用户自己的及公开知识库。前端保留已选 ID，搜索、重置只改变候选列表，不清空已选项。不能把旧 mock 的 `kb-core` 等示例 ID 当成真实 ID。

生成前重新检查知识库存在、未删除及用户访问权限。任何一项失效或越权都应返回明确错误，不静默忽略所选知识库。

**挂载方式尚未由这次 UI 字段要求明确：选择知识库不等于已经确认“运行时检索”或“原文件快照”。**

为复用现有生成能力，本期代码沿用已有原文件快照适配器：有权限且可读取的知识库原文件按类型进入文档 `references/`、图片/归档 `assets/` 或脚本 `scripts/`，使用统一 `resource_usage`，记录 ID 和哈希。该实现不代表已完成知识库运行时检索，也不代表正式挂载方式已由产品确定；若采用运行时检索，需改为保存关联并由运行模块读取，不伪造知识库内容。

新表单的原文件快照方案已校验：空知识库、文件缺失/为空、文件越界、未知类型或展开后超过资源数量上限返回错误，不发布包。旧合同空知识库警告行为保留，避免改变原 API 合同。原文件无需全部转换成 Markdown。

## 5. 合并后的资源上传

统一通过 `files` 上传。前后端统一白名单：脚本 `.py/.js/.sh/.bash/.ps1`，归档 `.zip/.whl/.gz/.tgz/.tar`，文档 `.md/.txt/.json/.csv/.pdf/.doc/.docx/.xls/.xlsx`，图片 `.png/.jpg/.jpeg`，扩展名不区分大小写。未知类型拒绝，不只依赖浏览器 `accept`。图片无需独立表单字段。

原先“参考资料入口”和“脚本入口”的两份数组不再要求前端组织。新增统一入口适配器，在服务端生成内部文件绑定：

| 文件类型 | 默认目录 | 处理方式 |
|---|---|---|
| `.py`、`.js` | `scripts/` | 作为脚本原文件保存，不执行 |
| `.md`、`.json`、`.xlsx` | `references/` | 默认作为参考资料保存，不提取或改写内容 |
| `.zip` | `assets/` | 作为资源/依赖归档原样保存，不解压、不安装 |
| `.png`、`.jpg`、`.jpeg` | `assets/` | 图片原样保存，生成相对链接和统一使用说明；不转成 Markdown、不做 OCR 或图像理解 |

这些是统一入口下的默认组织规则，属于平台约定，不是官方强制分类。扩展名只能辅助归类，不能证明文件安全或业务用途；JSON、Excel 是否用作输出模板，由统一资源说明表达，本期不为此再增加分类字段。

图片使用链路：开发者从资源上传入口选择图片 → 填写资源使用说明（例如“生成测试用例前，读取业务流程图”）→ 后端保存到 `assets/business-flow.png` → `SKILL.md` 写入 `[业务流程图](assets/business-flow.png)` 和说明 → Agent 使用 Skill 时读取图片。后端不自动改写开发者的执行指令；图片读取、理解能力及其验证属于运行端接入。

**实施状态：图片已设为 `asset` 并进入 `assets/`；前端提示、文件选择白名单及客户端校验已同步，后端仍独立校验。** 测试覆盖图片扩展名及大小写、原始字节/哈希、相对链接、缺少资源说明失败和 ZIP 下载后内容一致。引擎不解码或识别图片，扩展名校验不等同于内容安全扫描或有效图像检测。

新表单拒绝带目录分隔符、越界或系统保留名的上传文件名，按 NFKC/大小写检查同名上传，并拒绝空文件。现有生成器继续检查实际保存路径与文件冲突；有错误时不发布构建，上传暂存清理。

大小规则以2026-10-13老师要求及用户确认为准：单文件最多20MB（20,000,000字节）、每次最多直接上传5个，不设合计20MB限制；知识库展开后100个实际资源的工程上限单独保留并逐个校验大小。后端检查文件名、越界路径、同名冲突、哈希及引用，不执行脚本。ZIP原样保存，本期不需要Docker镜像上传；此前500MB已不再作为现行规则。

## 6. 请求与接口适配

采用“新表单 DTO → 内部 `SkillPackageSource` → 已有生成器”的结构，前端不再提交标准技术名、描述、版本、系统、团队或模型 Tier。接口状态如下：

| 接口 | 用途 |
|---|---|
| `GET /skills/name-availability?name=...&exclude_id=...` | 已实现：名称预检查，排除 ID 必须属于当前用户；最终约束仍在服务端写入时执行 |
| `POST /skills/` | 复用已存在接口，先创建禁用的技能记录，取得 `skill_id`；新建请求仅需业务名称，不由前端填写技术描述 |
| `POST /skills/form/builds` | 新版合同适配批次已实施（八步中的第 6 步）：统一六项表单生成，multipart 的 `source` 为 JSON 字符串，`files` 为重复文件字段；无附件时省略 `files` |

名称检查静态路由需要注册在已有 `GET /skills/{skill_id}` 之前；统一表单路由也需避免被 `/{skill_id}/builds` 匹配。旧接口保留，不能把中文 `skill_name` 错映射到旧标准 `name`。

`source` 示例：

```json
{
  "skill_id": "已创建的实际技能ID",
  "skill_name": "核心系统用例生成",
  "instructions": "读取用户需求，参考业务规则生成正向、异常和边界用例。关键信息缺失时列出待补充信息。",
  "knowledge_base_ids": ["实际知识库ID"],
  "resource_usage": "知识库用于核对支付业务规则；check_input.py 在生成前校验输入；依赖归档用于准备脚本环境。",
  "compatibility": "Python 3.12；依赖由运行环境预先提供。"
}
```

本阶段新建和编辑都由页面携带 `skill_id`，不增加用户填写项。为复用已有记录和前端重试流程，保留“创建记录 → 构建”两阶段；构建入口不会再创建一条新记录。无 `skill_id` 时返回字段错误。文件随 `files` 发送，不在 JSON 中传本地绝对路径。没有知识库或文件时 `resource_usage` 允许为空。

实际执行顺序：认证 → 当前技能权限 → 表单/上传元数据校验及内部绑定生成 → 在事务中检查并占用名称 → 知识库/文件检查 → 复用生成器 → 发布新构建 → 提交数据库事务并返回结果。技术名和描述由适配层生成。字段必填、条件说明、技能/知识库权限、数据库名称唯一性及资源类型校验已实施。失败不发布不完整的目录包，前端保留同一技能 ID 供重试。

首个新版构建基于技能 ID 的 SHA-256 摘要生成 `skill-<24位摘要>`。已有构建沿用最近一次服务端历史的技术名和版本；前端初始临时标识不参与生成，成功后回写后端返回的技术名、描述和版本。创建者从认证上下文取得，未提供实际归属的系统、团队等元信息不输出。

成功继续返回 `skill_id`、`build_id`、标准技术名、文件清单及现有查询/下载引用；业务失败沿用 `missing_fields`、`errors`，字段映射回六项表单。例如：

```json
{
  "valid": false,
  "missing_fields": [
    {"field": "resource_usage", "reason": "选择知识库或上传资源后，请填写资源使用说明"}
  ],
  "errors": [],
  "warnings": []
}
```

草稿允许指令和条件说明暂未完成，名称仍需非空且不重复；生成和调试前严格校验。当前草稿在浏览器本地，若前端继续采用此方式，保存草稿不等于后端已上传文件或已占用名称；真正发布时必须重新检查。服务端草稿管理不在本次改版中自动扩展。

## 7. 生成模板与保存

```markdown
---
name: skill-<后端生成的稳定标识>
description: <根据技能名称和执行指令生成的基础描述>
compatibility: <有内容时才输出>
metadata:
  display_name: <技能名称>
  version: "0.1.0"
  skill_id: <平台技能ID>
  creator_id: "<认证用户ID>"
---

# <技能名称>

## 执行指令
<完整执行指令>

## 资源使用说明
```
