## 一、先理解你要开发的东西

这里的“解析”是把结构化表单和实际资源文件转换成一个符合约定的 Skill 目录包：检查字段 → 补齐平台内部信息 → 整理资源 → 生成 `SKILL.md` → 保存构建 → 提供查询和完整 ZIP 下载。

例如，开发者填写“核心系统用例生成”、描述、版本 `0.2.0`、执行步骤，并上传 `flow.png` 和 `check.py`。引擎应生成：

```text
skill-<技能ID摘要>/
├── SKILL.md
├── assets/flow.png
└── scripts/check.py
```

其中 `SKILL.md` 包含开发者填写的描述、版本、执行指令和资源使用说明。图片与脚本保留原始内容。后端此时没有执行脚本、识别图片或调用模型；真正使用 Skill 的运行器以后从目录读取它。

```mermaid
flowchart LR
  A[开发者提交八项表单和文件] --> B[FastAPI 接口接收]
  B --> C[字段、名称、权限和资源校验]
  C --> D[转换为内部生成源]
  D --> E[生成 SKILL.md 并复制资源]
  E --> F[保存构建清单、目录及 ZIP]
  F --> G[返回构建结果与只读定义]
```

对新手来说，可以把“DTO”理解为接口接收的数据格式，“适配层”理解为字段转换函数，“生成器”理解为实际写文件的代码，“构建”理解为一次生成的结果。“版本号”是业务标签，`build_id` 是每次生成的唯一编号，两者不能混用。

## 四、八项业务字段的输入合同

| 页面字段 | 后端字段 | 生成时规则 | 写到哪里 |
|---|---|---|---|
| 技能名称 | `skill_name` | 必填；去首尾空白，1–128 字符；复用名称唯一性，编辑排除自身 | Skill 展示名、metadata.display_name、正文标题 |
| 描述 | `description` | 必填；去首尾空白后非空，最多 1024 字符；保留内部换行和内容；超长报错，不截断 | YAML description；构建源及已有 Skill.description |
| 版本号 | `version` | 必填；非空，最多 64 字符；按字符串保存 | metadata.version、构建清单 version/source.version |
| 执行指令 | `instructions` | 必填；非空，最多 100000 字符；包含步骤、业务约束及输入输出要求 | SKILL.md 正文和构建源 |
| 挂载知识库 | `knowledge_base_ids` | 选填；数组默认空；继续多选、去重并逐项校验权限 | 实际资源快照及服务端清单 |
| 资源上传 | multipart `files` | 选填；多个真实文件；检查类型、文件名、大小、数量及冲突 | scripts/references/assets 和清单 |
| 资源使用说明 | `resource_usage` | 无资源时选填；有任意知识库或文件时必填；最多 10000 字符 | 一个统一说明章节和构建源 |
| 运行环境要求 | `compatibility` | 选填；最多 500 字符；空则省略 | YAML compatibility |

保留 `skill_id` 作为页面携带的技术参数，不新增让用户手填的输入框。新建先由已有接口创建记录得到 ID；编辑使用原 ID，并验证属于当前用户。

名称继续复用当前技术约定：平台内未删除记录全局唯一，未启用记录也占名；按 NFKC、首尾空白和英文大小写比较，编辑排除自身，数据库名称键约束兜底。这个范围沿用已有实现，不代表本次重新增加了产品规则；团队后续确认范围时再统一调整。

版本格式暂按前端现状设计：允许 `0.2.0`、`v1.0.0` 等非空标签，不擅自强制三段式语义版本，也不自动升级。版本号不用于拼接服务器目录。建议界面说明采用统一写法，但它不是新增业务校验要求。

草稿继续由前端本地保存，可暂缺描述、版本、指令或资源说明。点击生成/进入调试前，八项规则必须通过服务端检查。保存草稿不代表文件已上传到后端或名称已在数据库占用。

### 新手需要理解的两层校验

前端检查用于及时提示，后端检查用于保证写入正确。即使页面必填，调用方仍可能绕过页面直接请求接口，所以后端必须再次检查。

建议沿用当前返回方式：DTO 对必填文本允许空默认值，以便业务校验集中返回 `missing_fields`；长度超限或类型错误由 DTO 返回字段错误。请求仍禁止任意传入 `creator_id`、保存路径、资源角色等内部信息。新增描述和版本应从“禁止字段”改为“明确接收字段”，不能直接取消所有额外字段校验。

## 五、从表单转换成标准 Skill

标准目录和 YAML 格式按 [Agent Skills 规范](https://agentskills.io/specification)。本平台将展示名、版本、技能 ID 等扩展信息统一放入字符串映射 `metadata`；描述和兼容要求使用标准字段。以下是平台目标模板，不是新增的 UI 字段。

```markdown
---
name: skill-<技能ID摘要>
description: 根据业务需求及规则生成正向、异常和边界测试用例，适用于功能测试设计。
compatibility: Python 3.12；所需依赖由运行环境提供。
metadata:
  display_name: 核心系统用例生成
  version: "0.2.0"
  skill_id: "实际技能ID"
  creator_id: "认证用户ID"
---

# 核心系统用例生成

## 执行指令
读取用户需求，参考业务规则生成测试用例。关键规则缺失时列出待补充信息。

## 资源使用说明
生成前读取 flow.png 确认业务流程；check.py 用于校验输入。

## 资源文件
- [业务流程图](assets/flow.png)
- [输入校验脚本](scripts/check.py)
```

没有填写 compatibility 时省略该字段；没有实际资源时不生成空目录或空资源章节。所有 YAML 由安全序列化生成，避免描述中的冒号、引号、换行破坏格式。长描述应报错，不再做旧版的自动截断。

转换原则：

- 新包的技术名继续由技能 ID 摘要生成；旧包沿用已有技术名，改展示名或版本不改技术名。
- `description = form.description`，不能重新套用“用于处理与……”前缀。
- `version = form.version`，历史只用于找稳定技术名，不覆盖本次版本。
- 创建者继续来自认证上下文；用户名不是开发者新增填写项。
- 执行指令和资源说明独立保存，不拼接后再丢失字段边界。
- 输入输出要求如果写在指令中，按文本完整保留；本引擎不自动把自然语言变成可执行验证规则。

## 六、资源如何处理

| 类型 | 后端目标目录 | 处理方式 |
|---|---|---|
| .py/.js/.sh/.bash/.ps1 | scripts/ | 原样复制，不执行 |
| .md/.txt/.json/.csv/.pdf/.doc/.docx/.xls/.xlsx | references/ | 原样复制，不统一转成 Markdown |
| .zip/.whl/.gz/.tgz/.tar | assets/ | 原样复制，不解压或安装 |
| .png/.jpg/.jpeg/.gif/.webp/.svg | assets/ | 原样复制，生成相对链接；不识别图片、不执行 SVG 内容 |

扩展名不区分大小写。GIF/WebP/SVG 是对当前前端白名单的新增对齐项；是否能被最终运行器识别，由运行器能力决定。保存成功只证明资源已正确入包。

2026-10-13 最新老师要求及用户确认：每个上传文件最多 **20MB（20,000,000字节）**，每次提交的全部直接上传文件最多 **5个**；等于上限允许，超过拒绝。前一次产品确认的500MB不再作为现行规则。本期仍不需要Docker镜像上传。**不另加资源合计20MB限制**，两个各15MB的文件允许生成。5个是本次所有files合计，重复选择或参考/脚本分入口不能绕过；服务层和适配器均检查。知识库展开后实际资源保留既有100个工程上限，这不是允许直接上传100个；挂载原文件同样逐个检查大小。未知类型、空文件、非法路径、同名、缺文件、权限及固定哈希校验保留。

两层检查采用同一单文件规则：`SkillPackageService` 分块接收上传文件时检查，`SkillPackageBuilder` 分块复制上传或挂载原文件时再次检查。超限返回对应 `files[index]` 或 `resources[index]` 的错误；临时文件自动清理，八项表单构建失败时回滚名称和描述。资源仍原样保存，不解包、不安装依赖、不执行脚本。

配置示例更新为 `SKILL_RESOURCE_MAX_BYTES=20000000`，上传数量使用共享常量`MAX_SKILL_UPLOAD_FILES=5`；旧 `SKILL_BUILD_MAX_BYTES` 已移除且不再生效。部署时已有单文件环境变量如为52428800或500000000，应改为20000000并重启。此规则只调整Skill解析引擎，不修改知识库模块自己的上传规则。

部署检查：服务器需核对代理整个请求限额、临时/构建磁盘及超时。5个各20MB的文件加表单和multipart开销可能略超100MB，不能把代理整个请求上限误设为20MB。仓库没有Nginx上传配置，本次未修改正式服务器。前端现行500MiB/100个需另外同步为20,000,000字节/5个；本批只修改后端与交接文档，不把旧前端测试当新规则已生效。

### 知识库在引擎中的边界

解析引擎接收真实知识库 ID，读取仓库已有 KnowledgeBase/Document 记录，验证当前用户访问权限，再把有权限的原文件复制进包。当前访问规则按实际用户/公开状态判断，前端“测试一组”等显示标签不能当作真实团队权限。

本方案继续沿用原文件快照，使 ZIP 包包含实际挂载文件，而不是只有 ID 或文件名。空库、缺原文件或不可读取时返回失败。只有向量切片而没有原文件时，不能宣称已生成完整资源包。

当前知识库模块尚未开发，本周不依赖它：knowledge_base_ids 传 []，引擎不查询知识库。用户可以完全不挂资源，或直接通过统一 files 入口上传。知识库入口保留，等对应模块完成再联调，不能把它列为本周生成/查询/下载的阻塞项。

知识库的新建、名称搜索、版本号存储和文档处理由对应后端模块负责。引擎只消费它的结果，不新增知识库表字段或搜索服务。若上游提供知识库版本，建议把构建时的 ID/版本/文档 ID/哈希记录在服务端快照清单；上游未提供版本时不编造，可先依靠文件 ID 和哈希追踪。

“取消独立文件资源管理库”是页面模块调整，不等于删除知识库原文件或取消 Skill 附件。引擎仍需要实际文件才能生成完整包，不能据此删除现有 Document 数据或文件存储。

新建知识库的“版本号必填”不等于你的引擎需要实现知识库版本管理。原文件快照和运行时知识库检索是两种不同方案；若团队后续改成运行时检索，需要另行调整挂载合同，不能将它们混作已完成能力。

## 七、接口设计与完整请求

尽量复用现有接口，不因为表单增加两项就重新搭后端框架。

| 接口 | 本引擎的用途 | 当前是否已有 |
|---|---|---|
| GET /skills/name-availability | 展示名预检查，编辑可排除自身 | 已有，继续复用 |
| POST /skills/ | 先创建禁用的技能记录，取得 ID | 已有，作为生成入口依赖 |
| POST /skills/form/builds | 接收八项合同及统一上传，生成构建 | 八项合同已适配并隔离验证 |
| GET /skills/{skill_id}/builds | 查询历史构建和版本 | 已有，继续复用 |
| GET /skills/{skill_id}/builds/{build_id} | 读取指定构建的定义、清单和目录 | 已有，作为调试定义数据源 |
| GET /skills/{skill_id}/builds/{build_id}/download | 下载完整 Skill ZIP | 已有，继续校验资源完整性 |

生成采用 multipart/form-data，因为一份请求既有 JSON 又有文件。`source` 是 JSON 字符串，多个文件放在重复的 `files` 字段；不能在 JSON 中只传本机路径代替文件内容。

当前 source 示例（需替换为真实技能 ID，并携带已有平台 Token）：

```json
{
  "skill_id": "实际技能ID",
  "skill_name": "核心系统用例生成",
  "description": "根据业务需求及规则生成测试用例，适用于功能测试设计。",
  "version": "0.2.0",
  "instructions": "读取需求，按规则生成正向、异常和边界场景；关键信息不足时列出待补充项。",
  "knowledge_base_ids": [],
  "resource_usage": "生成前读取 flow.png 确认业务流程；check.py 校验输入。",
  "compatibility": "Python 3.12"
}
```

随 files 上传 flow.png/check.py。没有任何资源时，resource_usage 可以为空。

建议处理顺序：认证与技能权限 → 八项合同校验 → 上传元数据归类 → 名称事务检查/占用 → 知识库和实际文件校验 → 生成目录及清单/ZIP → 成功保存本次描述并提交事务 → 返回构建。失败不能留下可被误用的半成品，资源失败需回滚本次名称/描述修改，复用已有暂存清理和发布逻辑。

业务成功继续检查 `status == "success"`，不能仅看 HTTP 200。失败字段与页面对应，例如：

```json
{
  "status": "failure",
  "data": {
    "valid": false,
    "missing_fields": [
      {"field": "description", "reason": "请填写描述"},
      {"field": "version", "reason": "请填写版本号"}
    ],
    "errors": [],
    "warnings": []
  }
}
```

前端字段错误映射需要接受 description/version；已有 name 对应技术名、skill_name 对应展示名的区别继续保留。本引擎不额外提供登录页，仍使用平台原有 Token；无会话演示不能绕过鉴权。

兼容范围：历史目录包以及旧 `/{skill_id}/builds`、分入口上传等接口保留；`/form/builds` 是本次升级的表单合同，旧六项调用方需补交描述和版本。不能一边声明它们必填，一边在新入口悄悄用默认值补齐。

## 八、给调试页面提供什么

“展示全部约束信息”由本引擎提供可靠的数据，而不是增加一个新的“全部约束”输入框。调试页面应先读取当前 `build_id` 的构建详情，使用其中的 `source` 和 `files` 展示：技能名称、描述、版本、执行指令、知识库关联、资源使用说明、环境要求及实际资源文件清单。

当前返回已有 `source` 和 `files`，初期直接复用即可，无需新增数据库表或单独的调试上下文接口。选择了旧构建就展示旧构建的定义，不能用后来编辑的本地草稿覆盖它。例如，v0.2.0 已生成后把表单改成 v0.3.0，但尚未再次生成，调试旧包时仍应展示 v0.2.0。

这些字段包含开发者声明的规则，不代表引擎已经把它们逐项执行或验证过。运行器实际生效的权限、超时或工具配置若需要展示，由运行器模块另行提供。

对话文本、粘贴的需求文档和调试时上传的文件是“一次运行的输入”。它们不是这个 Skill 的静态资源。本引擎不接收这些内容作为生成源，不自动塞进 references/assets，也不开发文档抽取、模型调用或沙箱执行。运行器后端接口由同事负责；交接时提供当前 skill_id、build_id 以及经过权限验证的构建目录和清单。

前端调试弹窗已经更新，但仍有“模拟沙箱”标记，不能把其成功输出作为真实 Skill 执行验收。

## 九、保存、版本和 ZIP 的关系

继续使用现有结构：

```text
<构建根目录>/<用户ID>/<技能ID>/<构建ID>/
├── manifest.json
├── package.zip
└── .claude/skills/<技术名>/
    ├── SKILL.md
    ├── references/<实际资料>
    ├── scripts/<实际脚本>
    └── assets/<实际图片或归档>
```

manifest 是服务端的一次构建记录，保存描述、版本、执行指令、资源说明、环境要求、文件路径/大小/哈希等。下载 ZIP 内包含 `<技术名>/SKILL.md` 和该目录下全部实际资源；服务端 manifest 不必为了“完整 ZIP”额外放入下载包。

同一个 Skill 可以有多次构建，每次 build_id 不同，即使提交的版本号相同也不覆盖旧包。版本只是标签，不擅自增加“同技能版本号唯一”规则。更改版本后新建构建，历史下载继续指向原来的包。

已有 Skill 模型包含 description，但没有独立 version 列。此次引擎不必增加 Skill.version：版本已能保存在构建清单和 source 中。当前记录的 description 可在构建成功后更新；历史构建的 description 从自己的快照读取。若其他模块以后需要数据库版本索引，由它们与团队另定，不预先扩展本任务。

完整性验证继续使用文件清单和哈希。缺资源或文件被修改拒绝下载；其他用户下载权限和直接上线状态由对应模块接入，不通过放宽构建所有者权限模拟。审批已取消。
