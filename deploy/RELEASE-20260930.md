目录结构：


合并时补齐了前端对 `queued` / `deleting` 的显示和轮询：提交删除后显示
“删除中”，后台清理完成并从文档列表消失后才移除前端条目；派发失败会提示。
删除部分文档不再从前端取消整个流水线。

## 服务器配置

保留服务器现有 `.env`，按 `.env.example` 对照补缺项。该文件被 Git 忽略，
不要把本机数据库地址、API 密钥或 Windows 路径提交到服务器代码中。
模型、Milvus collection、Embedding 维度和 Docling 离线目录继续使用服务器配置。
代码合并本身不搬运本地 MySQL 记录、PDF 产物或 Milvus 向量。

需核对的新增配置包括 `SUBQUERY_MAX_TOKENS=800`、`LLM_MAX_TOKENS=8192`，
以及 `.env.example` 中的子问题重试、回填、答案截断重试配置。
Docling 的模型目录需指向服务器已准备好的离线模型目录，不能直接使用本机
`D:/projects/agent-template-dev-jyy/` 路径。

本地验证复用 dev-jyy 虚拟环境，代码来自本发布分支。服务器使用其自身的虚拟环境。
仓库现有 Python 版本声明为 3.13；本机的 Python 3.12 测试通过不能替代服务器依赖核对。

## 数据库内容

本次提交同时包含模型、写入调用和 SQL：

| 对象 | 变更 | 提交文件 |
| --- | --- | --- |
| `rag_document` | `deleting_retry_count`、`deletion_retryable`、`deletion_error_type` | `resources/rag_document_deletion_migration.sql` |
| `llm_call_log` | 调用开始/结束/首 Token 时间、耗时、Token 数、输入输出、`created_time` 落库时间 | `resources/llm_call_log_schema.sql` |
| `rag_conversation_message` | `thinking_ms` 回写和接口读取 | 既有基础迁移 `migrations/models/1_20260817171209_None.py` |
| 反馈和映射证据表 | 继续保留既有表和迁移 | `migrations/models/3_*`、`4_*` |

当前后端会自动发现 `applications/*/models/*_model.py`，包含 `LLMCallLog`。
调用统计写入失败仅记录告警，不中断问答；上线后仍应验证统计表有新增记录。

升级时先备份服务器数据库，再核对已有列和迁移记录。
当前代码在 Linux 生产启动时会执行 Aerich `migrate` / `upgrade`，建议先只启动
一个 API 进程完成迁移并核对，再启动全部 API Worker、Celery Worker 和 Beat。

上面两个 SQL 文件也可供 DBA 审核和采用手工变更流程。
删除补偿 SQL 是一次性增量语句，字段已存在时不可重复执行。
LLM 建表 SQL 使用 `utf8mb4_0900_ai_ci`，要求支持该排序规则的 MySQL。
手工执行 SQL 后需要按服务器既有流程同步 Aerich 迁移记录；不要再把相同结构变更
作为未执行的迁移重复运行。不要同时混用两套迁移方式。

核对示例（在目标业务库执行）：

```sql
SHOW COLUMNS FROM rag_document WHERE Field IN
    ('deleting_retry_count', 'deletion_retryable', 'deletion_error_type');
SHOW COLUMNS FROM rag_conversation_message LIKE 'thinking_ms';
SHOW CREATE TABLE llm_call_log;
SELECT COUNT(*) AS call_count, MAX(created_time) AS latest_created_time
FROM llm_call_log;
```

## 部署和验收顺序

1. 拉取本发布分支，保留服务器配置与持久化目录；记录原版本以便回滚。
2. 暂停接收新解析任务，停止旧 API、Celery Worker 和 Beat；三者必须切到同一份代码。
3. 使用服务器虚拟环境核对依赖，按上面的单进程流程完成数据库变更。
4. 启动 API、Worker 和 Beat。API 默认 8519；Worker / Beat 启动方式仍见根目录 `celery_deploy.sh`。
5. 在 `frontend/` 中执行 `npm ci` 和 `npm run build`。
   无网服务器可以接收已经构建好的 `frontend/dist/`：`node frontend/server.js`
   只使用 Node 内置模块，运行静态服务不需要前端构建依赖。
6. 使用 Nginx 时把 `deploy/nginx.conf` 的 `root` 改为实际 `frontend/dist/` 路径。
   使用 Node 静态服务时设置 `PORT` 和 `BACKEND_URL`；默认端口为 3000，后端地址为 `http://127.0.0.1:8519`。
7. 验证 `/health`、`/api/models` 和文档列表；确认 Milvus 向量数及已有知识库仍正常。
8. 用临时小文档验证上传、解析、取消、Worker 失联状态更新、删除完成后文件和向量清理。
9. 验证普通问答、复杂问答、流式输出、会话历史和反馈，再检查 `llm_call_log` 中的新增记录。

Windows 的 `node_modules` 不应复制到 Linux 构建环境；可以直接交付已构建的静态文件，
或者在匹配服务器平台的构建机安装依赖后构建。

本分支不会提交 API 密钥、本地日志、问答测试输出、PDF、模型缓存和向量数据。
这些运行数据仍由服务器原有持久化目录与数据库管理。

## 9 月 30 日本地回归修复

实际 API、Celery Worker、MySQL 和 Milvus 联调后补齐以下问题：

- 删除任务改用当前 `milvus_store`，消除旧 `vector_rpc` 导入失败导致的删除滞留。
- 解析中途删除时，即使数据库尚未保存 input/output 路径，也按文档 ID 清理标准
  目录；拒绝根目录或越出配置目录的清理目标，避免遗留 Docling 产物。
- 取消后的重试/回滚先取得文档锁，再重置状态；Celery 消息 ID 通过 ContextVar
  传到异步执行线程，使预留锁、执行锁和失联锁释放使用同一标识。
- 回滚任务允许自己已提交的 `embedding` 状态，避免接口提交成功后 Worker 跳过回滚。
- 采纳映射提取增加独立输出预算与超时，截断时仅按配置有限重试；撤销采纳后不再
  被晚到的提取结果覆盖。新增配置 `MAPPING_EXTRACTION_MAX_TOKENS=8192`、
  `MAPPING_EXTRACTION_TIMEOUT=120`，服务器需对照现有 `.env` 核对。
- 前端首次访问采用后端默认模型；文档删除/结束后清理对应轮询定时器。

本地单元测试 80 项通过，前端 TypeScript 与生产构建通过；上传入库、更新回滚、
取消重试、Worker 失联恢复、真实问答、流式断线续接/停止、映射、反馈与统计落库
均有实际联调记录。Worker 失联与滞留删除测试只对临时文档模拟时间经过。
原 Visa 文档保留 6087 个向量分块，测试产物不进入发布源码。

运行中删除可能先因解析任务持锁而失败；当前巡检以 15 分钟滞留为补偿门槛，
Beat 每 5 分钟巡检。必须同时部署 Beat，不能把接口“已提交”当作物理清理完成。
查询改写低预算截断与 Milvus 原生 hybrid 降级仍需观察；功能回归结果不等同于
问答准确率评估，也不替代服务器 Python、依赖和数据库迁移验收。
